what changed
  the committing connection is reused, so the commit is visible without a second open
  task rows are read without the JSON columns; the transition history is two SQL statements, not one query per task
  row objects are built only for the 64 listed runs; counters, order and elapsed still cover every task
  while live.json is still the file this process wrote last, seq comes from memory and the previous document is not re-read
  no debounce, no fsync added or removed; the bytes for a given store state are the frozen earlier implementation
  (tests/test_telemetry_refresh_cost.py, 48 states)

what remains
  at 200 tasks the gain is above 2x (2.42x on the min, 2.16x on the median); at 13 tasks it is 1.33x, because the fixed cost of the lock and the write dominates
  the floor is the SQLite read (_load_tasks, still about half of derive_snapshot), the JSON encode and the atomic write
  a native derive_snapshot could still cut the SQL and the encode; it is not in this unit, and it pays only if a later measurement on a quiet host shows the Python floor is still the transition's largest cost
