How to read it
  The command that produced this file: /root/.cache/gsd-redact-work/venv/bin/python tests/perf/claims_engine.py   (defaults: 7 passes, 30 inputs, 3 passes for the 500-claim input)
  Figures are CPU of the measuring thread, never wall time; the host was saturated (loadavg above, 8 cores), which inflates every row the same way.
  Before any timing the script compared the adapter with the Python table for exactly these inputs (results and held view in acquisition order): equal.
  "one acquire of 50 claims" is the cheapest case (an empty table: nothing to collide with); the Python table is already cheap there, so the gain is small.
  "50 sequential acquires" is what select_batch does in a pass over 50 ready tasks that all declare claims; the 500 row is the same over 500 tasks (the
  4096-entry overlap cache of swarm.claims thrashes there, so warm and first sight cost the same).
  Adapter / raw native is the price of the Claim-object interface: tuples in, ClaimResult out, the journal kept for conflict mapping and fallback.
